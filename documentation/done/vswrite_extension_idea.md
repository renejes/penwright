Architekturanalyse und Marktstrategie: KI-gestützte WYSIWYG-Textverarbeitung auf Basis von Typst in IDE-Umgebungen1. Executive Summary und Problemstellung im Kontext der First PrinciplesDie vorliegende Architekturanalyse evaluiert die technische Machbarkeit, den optimalen Technologie-Stack sowie die strategische Markttauglichkeit eines hochkomplexen Softwarevorhabens. Das Ziel ist die Entwicklung einer Erweiterung für eine integrierte Entwicklungsumgebung (IDE), welche diese in eine versionierbare, KI-gestützte WYSIWYG-Textverarbeitung (What You See Is What You Get) für Nicht-Programmierer – insbesondere Akademiker, Autoren und Studierende – transformiert. Die Kerninnovation besteht darin, die Mächtigkeit einer klassischen "Codebase" (Versionierung, Modularität, Automatisierung) auf eine "Textbase" zu übertragen. Dabei sollen moderne, dateisystembasierte KI-Agenten wie Claude Code oder Google Anti-Gravity nahtlos in den Schreibprozess integriert werden, während im Hintergrund das moderne Kompilierungssystem Typst für den professionellen Dokumentenexport sorgt.Die Untersuchung dieses Vorhabens erfordert eine Rückbesinnung auf die First Principles der Datenrepräsentation und Synchronisation. Die Architektur steht vor einem fundamentalen, dialektischen Konflikt. Auf der einen Seite operieren moderne CLI-Agenten ausschließlich auf der Dateisystem-Ebene mit rohem Text. Sie modifizieren Dateien asynchron und iterativ, genau wie menschliche Entwickler in einer Codebase. Auf der anderen Seite erfordert eine zugängliche Textverarbeitung für Nicht-Programmierer ein visuelles WYSIWYG-Frontend. Moderne Editor-Frameworks wie TipTap (basierend auf ProseMirror) verwalten ihren Zustand jedoch als Abstract Syntax Tree (AST) im flüchtigen Arbeitsspeicher.Wenn ein KI-Agent eine Quelldatei im Hintergrund umschreibt, während der menschliche Nutzer gleichzeitig im visuellen Frontend interagiert, kollidieren zwei unabhängige "Wahrheiten" des Dokumentenzustands. Ohne eine kugelsichere Übersetzungsschicht und Synchronisationsarchitektur führt dieser Konflikt unweigerlich zum Verlust der Cursor-Position, zur Zerstörung des Dokumentenlayouts oder zum unwiderruflichen Datenverlust. Die nachfolgende Analyse dekonstruiert diesen Konflikt, definiert die technischen Brücken zwischen AST und Dateisystem und entwirft eine tragfähige Markteinführungs- und Monetarisierungsstrategie für das Ökosystem moderner Software-Marktplätze.2. Machbarkeit und Architektur-Konflikte: Die Konstante der SynchronisationDie Bewältigung der Diskrepanz zwischen der dateibasierten Arbeitsweise von KI-Agenten und der speicherbasierten Zustandsverwaltung des WYSIWYG-Editors bildet das architektonische Fundament des Projekts. Die technische Herausforderung liegt nicht im Erkennen von Dateiänderungen an sich, sondern in der konfliktfreien, bidirektionalen Zusammenführung (Reconciliation) von asynchronen Modifikationen.2.1. Das Paradigma der Datenmanipulation: AST versus Raw TextUm die Tiefe des Konflikts zu verstehen, muss die Funktionsweise von ProseMirror, der Engine hinter TipTap, betrachtet werden. ProseMirror operiert nicht auf Basis von veränderlichem HTML oder simplen Strings, sondern nutzt eine strikt typisierte, baumartige Datenstruktur (Document Model). Jegliche Änderung an diesem Dokument – sei es ein Tastenanschlag, das Einfügen eines Bildes oder das Anwenden einer Fettformatierung – wird als formelle "Transaktion" modelliert, die aus atomaren "Steps" besteht. Diese Transaktionen werden auf den aktuellen Editor-Zustand (EditorState) angewendet, um einen neuen, unveränderlichen Zustand zu erzeugen, der anschließend gerendert wird. Dieser funktionale Ansatz garantiert eine fehlerfreie Undo-Historie und ein stabiles Verhalten des Cursors (Selection).CLI-Agenten wie Claude Code haben keine Kenntnis von diesem internen Transaktionssystem. Sie lesen die .typ- oder .md-Dateien vom Speichermedium, generieren neue Textpassagen und überschreiben die Dateien über Standard-I/O-Operationen. Eine IDE wie Visual Studio Code registriert diese Dateisystemänderung über interne File-Watcher. Wird der geänderte Text nun nahtlos und unstrukturiert in den laufenden WYSIWYG-Editor geladen, behandelt ProseMirror dies als kompletten Austausch des Dokuments. Das Resultat ist katastrophal für die User Experience: Der interne Zustand wird verworfen, die Cursor-Position geht verloren und sämtliche nicht gespeicherten Eingaben des Nutzers werden überschrieben.Daten-ParadigmaLokationModifikationsartKonfliktpotenzial bei asynchronen UpdatesWYSIWYG (TipTap/ProseMirror)Arbeitsspeicher (RAM)Transaktionen & Steps (EditorState.apply)Verlust von Cursor-Position, Undo-Historie brichtCLI KI-Agenten (Claude Code)Dateisystem (Disk)Rohe I/O-Schreibzugriffe (String Replacement)Überschreiben von ungespeicherten Nutzer-Eingaben2.2. Lösungsarchitekturen für die KonfliktauflösungDie Analyse ergibt, dass eine triviale Überschreibung ausgeschlossen ist. Stattdessen muss die IDE-Extension als intelligenter Mediator fungieren, der rohe Textänderungen des Dateisystems in native ProseMirror-Transaktionen übersetzt. Hierfür stehen zwei primäre Architekturmuster zur Verfügung: Operational Transformation (OT) mittels Diffing und Conflict-free Replicated Data Types (CRDT).2.2.1. Der algorithmische Diff-Match-Patch Ansatz (Empfohlen)Die effizienteste und für das Dateisystem am besten geeignete Methode ist die Implementierung eines robusten Diffing-Algorithmus, wie beispielsweise Google's diff-match-patch. Die Architektur sieht folgenden Datenfluss vor:Wenn der KI-Agent eine Datei ändert, fängt die IDE-Extension dieses Event über die API (z.B. vscode.workspace.onDidChangeTextDocument) ab. Bevor der neue Text dem Editor übergeben wird, vergleicht der Algorithmus den neuen Dateisystem-Text mit dem Text, der dem aktuellen AST des Editors entspricht. Der Algorithmus identifiziert exakte Einfügungen (Insertions) und Löschungen (Deletions) auf Zeichenebene.Diese isolierten Änderungen werden anschließend mit den relativen Positionen (ResolvedPos) des ProseMirror-Dokuments abgeglichen. Die Extension generiert programmatisch ProseMirror-Transaktionen (z.B. tr.replaceWith für Einfügungen oder tr.delete für Entfernungen) und appliziert diese auf den laufenden Editor.Der immense Vorteil dieser Architektur: Da die Änderungen als native Transaktionen eingespeist werden, greift das interne Mapping-System von ProseMirror. Der Cursor des Nutzers wird automatisch und mathematisch korrekt verschoben, selbst wenn die KI wenige Zeilen darüber oder darunter massiv Text einfügt. Zudem bleibt die Undo-Historie des Nutzers intakt, da die KI-Änderungen lediglich als zusätzliche Schritte in den Protokollverlauf aufgenommen werden.2.2.2. Der CRDT-basierte Ansatz (Alternative)Eine alternative Architektur basiert auf Conflict-free Replicated Data Types (CRDT), spezifisch unter Nutzung der Yjs-Bibliothek, für die TipTap exzellente native Unterstützung bietet. CRDTs wurden originär für die synchrone Echtzeit-Kollaboration zwischen mehreren Web-Clients entwickelt, bei der Operationen kommutativ sind und Konflikte mathematisch ohne zentrale Instanz aufgelöst werden.In diesem Szenario würde die IDE-Extension im Hintergrund einen eigenen Yjs-Dokumentenzustand verwalten. Externe Dateiänderungen müssten als Yjs-Updates injiziert werden. Während dieser Ansatz bei kollaborativen Web-Applikationen überlegen ist, erweist er sich in einem stark dateisystemzentrierten Workflow mit CLI-Agenten als übermäßig komplex. CRDTs verwalten historische Metadaten und "Tombstones" für gelöschte Zeichen, was zu einem Overhead führt, der bei einfachen Textdateien auf der Festplatte nicht nativ abgebildet werden kann. Da die KI-Agenten zwingend eine saubere, flache Textdatei als Input/Output erwarten, müsste der Yjs-State kontinuierlich in Rohtext dekonstruiert und wieder rekonstruiert werden, was fehleranfälliger ist als der präzise Diff-Match-Patch-Ansatz.3. Die bidirektionale Brücke: WYSIWYG, AST und Typst-KompilierungDie Übertragung der "Codebase"-Mächtigkeit auf eine "Textbase" bedingt, dass das Backend-Format extrem robust, maschinenlesbar und kompilierbar ist. Das Projekt zielt darauf ab, LaTeX durch Typst zu ersetzen. Typst zeichnet sich durch inkrementelle Kompilierung in Millisekunden, eine saubere, an Rust angelehnte Syntax und überlegene Fehlerbehandlung aus. Für Nicht-Programmierer muss diese Syntax jedoch vollständig hinter einem vertrauten WYSIWYG-Interface abstrahiert werden.3.1. Strukturierung des AST-zu-Typst SerializersWenn der Nutzer im TipTap-Frontend agiert, werden die Daten im JSON-Format gemäß des definierten Schemas strukturiert. Eine Kernaufgabe der Architektur ist die Entwicklung eines dedizierten Serializers, der diesen AST (Abstract Syntax Tree) deterministisch in Typst-Markup übersetzt.Während TipTap native Export-Module für HTML oder Markdown bereitstellt , erfordert Typst eine spezialisierte Logik. Die Extension muss den TipTap-JSON-Baum iterativ traversieren. Ein heading-Knoten mit dem Level 2 wird in == Überschrift übersetzt, ein bold-Mark in *Text* und eine Tabelle muss in die table()-Funktionssyntax von Typst transformiert werden. Die Umsetzung eines solchen Serializers ist technologisch geradlinig, da der AST stark strukturiert ist und Typst klare syntaktische Äquivalente für alle gängigen Textbausteine bietet.TipTap AST ElementTypst Markup / CodeArchitektur-RelevanzNode: Heading (Level 1)= TitelStrukturelle Hierarchie für das MasterfileMark: Bold*Text*Inline-FormatierungNode: Math (prosemirror-math)$ a^2 + b^2 = c^2 $Nativer Support für komplexe GleichungenNode: Mention/Citation@author2026Verknüpfung mit externer Bibliographie (.bib)Node: Table#table(columns: 2, [...])Funktionsaufrufe für komplexe Layouts3.2. Die Herausforderung der Typst-zu-AST DeserialisierungWeit komplexer gestaltet sich die Rückübersetzung (Deserialisierung). Wenn der KI-Agent komplexe Textabschnitte in Typst-Syntax generiert, muss dieser Rohtext wieder in den TipTap-AST überführt werden, um visuell im Editor dargestellt zu werden. Reguläre Ausdrücke (Regex) scheitern hierbei an verschachtelten Strukturen, rekursiven Funktionen oder komplexen mathematischen Umgebungen.Die Lösung liegt in der Nutzung von vollständigen AST-Parsern aus dem Typst-Ökosystem. Das Open-Source-Projekt Tylax, entwickelt in Rust, demonstriert eindrucksvoll, wie komplexe LaTeX- und Typst-Dokumente über High-Performance-Parser (wie mitex-parser und typst-syntax) in einen AST überführt werden können. Die Architektur für die geplante IDE-Extension muss ähnlich aufgebaut sein: Der Typst-Quellcode wird durch eine via WebAssembly (WASM) in die Extension eingebundene Parser-Bibliothek analysiert und in eine Zwischenrepräsentation (Intermediate Representation) umgewandelt. Diese Zwischenrepräsentation wird anschließend auf die JSON-Struktur des TipTap-Schemas gemappt. Dieser First-Principles-Ansatz der vollständigen syntaktischen Analyse ist die einzige Methodik, die garantiert, dass von der KI generierte Typst-Funktionen (wie #let oder #for Loops) den visuellen Editor nicht zum Absturz bringen.3.3. Orchestrierung der KompilierungEin entscheidender Aspekt der Markttauglichkeit ist der PDF-Export. Typst ist ein hochoptimierter, in Rust geschriebener CLI-Compiler. Die IDE-Extension muss den Compiler im Watch-Modus im Hintergrund orchestrieren (typst watch). Sobald der Nutzer Änderungen im TipTap-Editor vornimmt, serialisiert die Extension den AST in die zugrunde liegende .typ-Datei und speichert diese auf dem Dateisystem. Der Typst-Compiler registriert das File-System-Event und generiert in wenigen Millisekunden das resultierende PDF. Durch die Bereitstellung eines gespaltenen Ansichtsfensters (Split View) in der IDE kann der Nutzer links visuell in TipTap schreiben, während rechts das finale PDF in Echtzeit aktualisiert wird – eine Kombination, die die Usability traditioneller Word-Prozessoren mit der typografischen Perfektion von Code-Kompilern vereint.4. Die Wahl des Editor-Frameworks: TipTap vs. Lexical vs. SlateDas visuelle Herzstück des Projekts erfordert ein robustes Headless-Editor-Framework.TipTap (ProseMirror-basiert): Bietet eine hervorragende Abstraktionsschicht über das extrem komplexe, aber mathematisch präzise ProseMirror-Framework. Es arbeitet mit einem schema-basierten Dokumentenmodell und manipulierbaren Transaktionen. Es ist hochgradig erweiterbar, agnostisch gegenüber UI-Frameworks (React, Vue) und bietet von Haus aus Unterstützung für kollaborative Strukturen.Lexical (Meta): Ein modernes, auf React zentriertes Framework, das durch Performance und ein eigenes State-Reconciliation-System glänzt. Lexical ist sehr zukunftssicher, erfordert jedoch ein tiefes Verständnis von React-Paradigmen und weicht stark von traditionellen DOM-Manipulationskonzepten ab.Slate: Bietet die geringste Out-of-the-Box-Funktionalität und erfordert den höchsten Entwicklungsaufwand, da nahezu jede Basis-Interaktion selbst definiert werden muss.Empfehlung: TipTap ist für dieses Vorhaben die optimale Wahl. Der entscheidende Faktor ist der Zugriff auf die ProseMirror-APIs (@tiptap/pm). Da die Synchronisation mit externen Dateisystemänderungen durch KI-Agenten die Umwandlung von Text-Diffs in strukturierte Editor-Transaktionen erfordert, bietet die zugrundeliegende ProseMirror-Engine die benötigte mathematische Strenge (Position Mapping, Step Inversion). Zudem existiert für ProseMirror bereits das Plugin prosemirror-math, welches für die akademische Zielgruppe und die Typst-Kompilierung von Gleichungen unabdingbar ist.4.3. Implementierung der Projekt-Scaffolding- und ZitationsarchitekturEin wesentliches Feature der Extension ist das "Project-Scaffolding" für Nicht-Programmierer. Beim Erstellen eines neuen Projekts muss die Extension über die VS Code Workspace API automatisch eine strukturierte Ordnerhierarchie anlegen:Ein master.typ File als Root-Dokument, das globale Typst-Regeln (#set page(), #set text()) definiert.Einen Ordner /chapters für die modularen Textinhalte.Einen Ordner /sources für Literaturdatenbanken (z.B. bibliography.bib oder Zotero-Exporte).Das integrierte Quellenmanagement wird durch die Kombination aus TipTap und Typst stark vereinfacht. Typst verfügt über einen nativen Compiler für Bibliografien. Die IDE-Extension analysiert die .bib-Datei im Workspace. Im TipTap-Editor wird ein angepasster Mention-Node (@) implementiert, der als Autocomplete-Dropdown fungiert und die Literaturdatenbank durchsucht. Bei Auswahl wird im AST ein Zitationsknoten eingefügt, der beim Export als @citekey im Typst-Quelltext serialisiert wird.5. Orchestrierung der KI-Integration: Der Agenten-WorkflowDie Prämisse, moderne KI-Agenten (Claude Code, Google Anti-Gravity) in die Textverarbeitung einzubinden, stellt das innovativste Element der Architektur dar. Agenten differenzieren sich von simplen Chatbots (wie ChatGPT) durch ihre Autonomie: Sie können Verzeichnisse analysieren, Dateien lesen, modifizieren und CLI-Befehle ausführen.5.1. Die Extension als Wrapper und BrückeUm die Zusammenarbeit zwischen der lokalen Extension-UI (TipTap) und den externen Agenten zu orchestrieren, muss die IDE-Extension zwingend als intelligenter Wrapper fungieren. Die KI-Agenten operieren nativ im Terminal der IDE. Wenn der Nutzer im WYSIWYG-Editor eine Anweisung gibt (z.B. "Überarbeite die Methodik im aktuellen Kapitel und füge fehlende Zitate aus der Quellen-Datei ein"), darf diese Anweisung nicht isoliert an ein LLM gesendet werden.Die Architektur für diese Orchestrierung basiert auf Inter-Process Communication (IPC). Die VS Code Extension liest den markierten Text und die Cursor-Position aus dem TipTap-AST aus, identifiziert die zugehörige Zeile im zugrundeliegenden .typ-Dokument und generiert einen formatierten CLI-Aufruf. Die Extension initiiert den Agenten (z.B. claude "Überarbeite Zeile 45 bis 90 in chapter2.typ...") als Hintergrundprozess im Terminal.5.2. Integration mittels Model Context Protocol (MCP)Der fortschrittlichste Ansatz zur nahtlosen Integration ist die Nutzung des Model Context Protocol (MCP), welches von Anthropic eingeführt wurde und sich rasant als Branchenstandard etabliert. Anstatt dem Agenten nur rohen Dateisystemzugriff zu gewähren, kann die VS Code Extension einen eigenen lokalen MCP-Server betreiben.Dieser MCP-Server stellt dem Agenten spezifische "Tools" zur Verfügung. Wenn der Agent aufgerufen wird, kann er Funktionen der IDE-Extension ansteuern, wie beispielsweise read_current_editor_state(), list_available_citations() oder get_document_outline(). Dies löst das Problem des fehlenden Kontexts drastisch. Der Agent versteht die logische Struktur des Dokuments jenseits der bloßen Zeichenketten, verifiziert Zitate gegen die .bib-Datei und modifiziert das Dokument strukturell sauber.Änderungen, die der Agent vornimmt, werden wiederum über den in Kapitel 2 beschriebenen Diff-Match-Patch-Mechanismus abgefangen und sanft in den WYSIWYG-Editor des Nutzers zurückgeschrieben. Fortschrittsberichte und interne Überlegungen des Agenten ("Thought Process") können von der Extension über die JSONL-Logs des Agenten ausgelesen und als dezente UI-Overlays im Editor angezeigt werden, um dem Nutzer Transparenz über die autonomen Handlungen der KI zu geben.6. Marktanalyse, Zielgruppe und WettbewerbslandschaftDie Überführung dieser technologischen Architektur in ein wirtschaftlich tragfähiges Produkt erfordert eine rigorose Marktanalyse. Die Hypothese lautet: Es existiert ein hochprofitabler Nischenmarkt von Akademikern, Autoren und Forschern, die die Produktivität von Code-Infrastruktur (Versionierung, Automatisierung, Agentic AI) benötigen, aber durch die kryptischen Schnittstellen klassischer Editoren abgeschreckt werden.6.1. Der Paradigmenwechsel von LaTeX zu TypstSeit Jahrzehnten monopolisiert LaTeX das wissenschaftliche Publizieren. Es leidet jedoch unter gravierenden Schwächen: Die Kompilierung komplexer Dokumente (z.B. Dissertationen) dauert oft Minuten, die Fehlermeldungen ("Missing $ inserted") sind frustrierend und die Integration verschiedener Pakete führt zu Inkompatibilitäten. Typst wurde entwickelt, um dieses Monopol zu brechen. Es kompiliert inkrementell in Sekundenbruchteilen und bietet lesbare Fehlermeldungen.Die Adoptionsrate von Typst steigt rapide, insbesondere an Universitäten. Dennoch bleibt eine erhebliche Einstiegshürde: Typst ist eine funktionale Programmiersprache. Viele Nutzer der Geisteswissenschaften oder kreative Autoren weigern sich, Code zu schreiben, und verbleiben bei MS Word oder Google Docs, obwohl diese bei komplexen Layouts, Querverweisen und Literaturverzeichnissen kapitulieren. Ein WYSIWYG-Editor, der im Hintergrund Typst generiert, schließt exakt diese Lücke.6.2. Plattform-Ökonomie und MonetarisierungsstrategienDie strategische Entscheidung, das Produkt als IDE-Extension (VS Code) auszuliefern, birgt erhebliche Herausforderungen bezüglich der Monetarisierung. Der Markt für Entwicklerwerkzeuge ist geprägt von spezifischen Erwartungshaltungen der Nutzerschaft.7.1. Das VS Code Marketplace-DilemmaMicrosoft stellt im VS Code Marketplace keine native Infrastruktur für den direkten Verkauf von Extensions bereit. Die Kategorisierung erlaubt zwar Labels wie "Free Trial", der Checkout-Prozess, das Lizenzmanagement und die steuerliche Abwicklung müssen jedoch extern durch den Entwickler implementiert werden. Diese strukturelle Gegebenheit hat dazu geführt, dass Entwickler eine weitreichende Open-Source- und Gratiskultur etabliert haben. Eine harte Paywall vor dem Download würde die Nutzerakquise extrem limitieren und das Wachstum hemmen.7.2. Implementierung eines Freemium- und License-Key-ModellsUm die Extension erfolgreich zu monetarisieren, muss das etablierte SaaS-Muster der Softwareindustrie auf die IDE-Architektur adaptiert werden: ein hybrides Freemium-Modell mit externen License Keys.Die Extension wird kostenlos im Marketplace angeboten. Die Kernfunktionen – das Projekt-Scaffolding, der Basis-WYSIWYG-Editor (TipTap) und die lokale Typst-Kompilierung – bleiben für alle Nutzer gratis zugänglich. Dies sichert eine hohe Verbreitung, organischen Traffic und den Aufbau einer Community. Die Analyse präferiert Lemon Squeezy deutlich. Für Softwareprodukte bietet es weitaus bessere Konditionen als Gumroad. Die API von Lemon Squeezy ist prädestiniert für IDE-Extensions: Der Nutzer schließt auf einer externen Landing-Page ein Abonnement (z.B. $8/Monat) ab und erhält einen Lizenzschlüssel. Dieser Schlüssel ist kryptografisch an den Status des Abonnements gebunden.Der Nutzer trägt diesen Schlüssel in die Einstellungen der VS Code Extension ein. Die Extension kontaktiert beim Start asynchron den Lemon Squeezy Server, validiert den Status und schaltet die Premium-UI-Elemente im TipTap-Editor frei. Um Serverkosten und Latenzen zu minimieren, sollte die Validierung lokal im Client zwischengespeichert (gecached) werden und nur periodisch oder bei Versionsupdates zwingend eine Netzwerkverbindung erfordern. Durch dieses Setup wird die Extension hochprofitabel, ohne Microsofts fehlende Marketplace-Monetarisierung als Hindernis zu haben.8. Finale Projekteinschätzung und AusblickDas Projektvorhaben, eine IDE durch eine WYSIWYG-Typst-Extension für Nicht-Programmierer zu erschließen und mit autonomen KI-Agenten zu verzahnen, erhält nach tiefgreifender Architekturanalyse eine definitive "Go"-Entscheidung.Die Konzeption ist technologisch ambitioniert, aber durch die gezielte Auswahl moderner First-Principles-Technologien (VS Code CustomTextEditorProvider, TipTap, Typst-Kompilierung, MCP-Server) vollständig realisierbar. Die größte technische Hürde – der Architekturkonflikt zwischen dem In-Memory-AST des Editors und den manipulativen Dateisystemeingriffen der CLI-Agenten – kann durch die Implementierung eines robusten Diff-Match-Patch-Algorithmus gelöst werden, der externe Änderungen verlustfrei in native ProseMirror-Transaktionen überführt.Wirtschaftlich adressiert das Projekt ein enormes Vakuum im akademischen und literarischen Bereich. Es befreit Nutzer von der technologischen Schuld veralteter LaTeX-Pipelines und den Unzulänglichkeiten von Cloud-Word-Prozessoren, indem es die Stabilität einer Entwickler-Codebase (Git, autonome KI-Refaktorisierung) auf Textdokumente anwendet. Gepaart mit einer sauberen Freemium-SaaS-Monetarisierungsstrategie über externe Lizenzprovider wie Lemon Squeezy birgt das Projekt das Potenzial, einen neuen Goldstandard für professionelles Schreiben zu etablieren.
